## 1. 文档目的

把《卦锻》的核心玩法拆成**可独立评审、可独立开发、可独立验证**的模块文档。每份模块文档只回答三件事：

1. 这个模块**做什么**、玩家看到什么；
2. 这个模块**怎么运转**、有哪些规则与数值；
3. 这个模块**和谁对接**、边界情况怎么处理。

本目录是“流程与规则”的详细描述；`../核心玩法策划.md` 是总纲与设计依据；`../视觉设计风格.md` 是视觉与动效规范；`../../prototype/` 是当前 UI 原型图。

## 4. 全局一图流

```
启动游戏
   │
   ▼
主界面 ──► 图鉴 / 设置 / 退出
   │
   ▼
开局准备：选择道途 → 选择初始武器/功法 → 确认开局
   │
   ▼
修行历劫（一局）
   │
   ├─ 炼气期：炼气一层 → 炼气圆满 → 筑基渡劫
   │                                      │
   │                              渡劫成功 → 晋升筑基
   │
   ├─ 筑基期：筑基初期 → 筑基后期 → 金丹渡劫
   │                                      │
   │                              渡劫成功 → 晋升金丹
   │
   ├─ 金丹期：金丹初期 → 金丹后期 → 元婴渡劫
   │                                      │
   │                              渡劫成功 → 晋升元婴
   │
   ▼
通关结算 / 失败结算
   │
   ▼
获得道行 → 局外解锁（武器/法宝/符箓/道途/天劫）
   │
   ▼
回到主界面 → 下一局（可挑战更高天劫）
```

> 每场战斗的详细回合流程见 `03-战斗流程.md`；一局内坊市/奇遇的插入点见 `02-单局历劫流程.md`。

## 6. 全局术语速查

| 术语 | 定义 | 详见 |
|------|------|------|
| 修行历劫 | 一局游戏的正式名称：从炼气期起步，逐境界突破 | 02 |
| 境界 | 局内进度段：炼气期 → 筑基期 → 金丹期 →（长线）元婴及以上 | 02、09 |
| 守关一 / 守关二 | 每境界的前两场战斗，分别偏普通与精英 | 02、07 |
| 渡劫 | 每境界的第三场战斗（Boss）；胜利即晋升下一境界 | 02、07、09 |
| 天劫 | 局外难度词条，与局内“渡劫”区分 | 09 |
| 战斗快照 | 玩家回合开始、尚未行动的完整战斗状态 | 13 |
| 继续游戏 | 主界面读取存档并恢复到对应页面的入口 | 01、13 |
| 八卦牌 | 牌堆中的基础牌，共 8 种卦，有品级/卦力/词缀 | 04 |
| 内卦 / 下卦 | 先选、摆在下方的牌，决定卦象行为与攻击五行 | 03、04 |
| 外卦 / 上卦 | 后选、摆在上方的牌，决定卦象修饰 | 03、04 |
| 卦象 | 内 + 外合成的 64 卦之一，即本作“牌型” | 04 |
| 卦力 | 牌提供的伤害基数，受品级影响 | 04 |
| 附魔 | 卦象对武器/功法的短持续写入效果 | 05 |
| 法宝 | 被动构筑位（对标 Joker），最多 4~5 个 | 06 |
| 符箓 | 一次性消耗品（对标塔罗/星球牌） | 06 |
| 灵力 | 每回合出牌资源，每手消耗 1 点 | 03、04 |
| 灵石 | 局内货币，用于坊市购买与刷新 | 08 |
| 道行 | 局外货币，用于永久解锁 | 09 |
| 熟练度 / 精通 | 单个卦象的使用成长与图鉴加成 | 04、10 |

## 7. 数值标注约定

文档中的数值统一使用以下标签，避免把“假设”误当“定案”：

| 标签 | 含义 |
|------|------|
| `[已定]` | 已评审拍板，改动需走变更记录 |
| `[v1假设]` | 原型默认值，允许 playtest 后调整 |
| `[待验证]` | 需要专门测试验证的假设 |
| `[未接线]` | 文档已描述，但当前原型/代码尚未接入，必须标 TODO |

> 所有数值都应配置化；模块文档只描述规则与默认值，不把数值写死在逻辑里。

## 8. 文档维护约定

1. 模块文档只描述本模块；跨模块规则写在“与其他模块的接口”一节。
2. 修改任何“已定”规则，必须同步更新 `../核心玩法策划.md` 与相关模块文档。
3. 不引入新基类、新中间件、新事件总线、新 DI 等架构，除非总纲明确要求。
4. 空方法、假实现、未接线能力必须在文档或代码中标注 `[未接线]` + TODO。
5. 每份模块文档末尾保留“待验证问题”，作为 playtest 清单。
