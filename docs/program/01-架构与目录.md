# 01｜架构与目录

> 版本：v0.1｜依赖：[README.md](README.md)

## 1. 技术基线

- Unity：`2022.3.62f3c1`
- 渲染：URP 2D Renderer
- UI：uGUI + TextMeshPro
- 语言：C#
- 测试：Unity Test Framework
- 存档：JSON + `Application.persistentDataPath`
- 输入：优先使用 Unity UI 事件系统；手柄需求确认后引入 Input System

## 2. 架构目标

本作是回合制卡牌战斗，不需要帧同步、物理驱动或大规模实体模拟。架构重点不是性能，而是：

1. 战斗规则集中、可测试。
2. 预览和结算一致。
3. UI 表现不反向污染战斗状态。
4. 64 卦和法宝效果可以数据化扩展。

## 3. 模块职责

```text
BattleController
  ├─ 驱动战斗状态机
  ├─ 接收玩家指令
  └─ 调用 Calculator / Resolver

BattleCalculator
  ├─ 读取当前状态
  ├─ 计算卦象、伤害、状态和触发顺序
  └─ 输出 BattleCalculation，不修改状态

BattleResolver
  ├─ 将 BattleCalculation 应用到 BattleState
  └─ 生成可播放的 BattleEvent

BattleView
  ├─ 展示 BattleState
  ├─ 接收输入并转发 BattleCommand
  └─ 按顺序播放 BattleEvent
```

职责边界：

| 层 | 可以依赖 | 禁止 |
|---|---|---|
| 战斗核心 | C# 标准库、数据定义 | UnityEngine UI、MonoBehaviour 生命周期 |
| 表现层 | 战斗核心、Unity API | 直接修改战斗数值 |
| 配置层 | CSV 配置、数据定义 | 保存单场战斗运行状态 |
| UI | BattleView、配置展示数据 | 自行推导伤害公式 |

## 4. 运行时数据流

```text
玩家点击/选择
    ↓
BattleCommand
    ↓
BattleController.Validate()
    ↓
BattleCalculator.Calculate()
    ↓
BattleCalculation
    ├─ 预览结果 → UI 显示
    └─ 执行结果 → BattleResolver.Apply()
                       ↓
                  BattleState 更新
                       ↓
                  BattleEvent 队列
                       ↓
                  BattleView 顺序播放
```

关键约束：

- `BattleCalculator` 不修改 `BattleState`。
- `BattleResolver` 不直接操作 UI。
- `BattleView` 不计算五行、倍率、会心或法宝收益。
- 一个玩家操作只产生一个逻辑结果，表现动画可以拆成多个事件。

MVP 建议目录：

```text
Assets/

      BattleResolver.cs

      BattleEvent.cs
      CardInstance.cs
      StatusInstance.cs

    Data/
      Definitions/
      Databases/
      Enums/
    UI/
      Battle/
      Common/
    Run/
  Data/
    Trigrams/
    Hexagrams/
    Weapons/
    Artifacts/
    Talismans/
    Enemies/
    Statuses/
  Prefabs/
    UI/
    Battle/
  Tests/
    EditMode/
    PlayMode/
```

说明：

- MVP 初期不拆大量 Assembly Definition，保持默认程序集；纯逻辑类不引用 Unity UI，仍可单独测试。
- 当编译时间、依赖边界或测试隔离成为实际问题时，再按需拆 `Game.Runtime`、`Game.Editor`、`Game.Tests`。
- 不建立空目录；目录按首个实际文件出现时创建。

## 6. 场景规划

| 场景 | 职责 |
|---|---|
| `Boot` | 初始化配置数据库、读取设置和存档，进入主菜单 |
| `MainMenu` | 开始游戏、继续、设置、图鉴入口 |
| `Battle` | 单场战斗，包含完整战斗 HUD |

局内地图、坊市和奇遇在 MVP 后期加入。若它们都是 UI 页面，可以优先在同一 `Run` 场景内切换面板，不为每个页面创建独立场景。

## 7. 状态生命周期

### 7.1 战斗状态

`BattleState` 只保存一场战斗内需要持续存在的数据：

- 玩家 HP、护盾、灵力、状态
- 武器运行时数据
- 牌堆、弃牌堆、手牌
- 附魔槽
- 敌人 HP、状态、当前意图
- 当前回合数和战斗阶段
- 随机数状态
- 战斗结果

战斗结束后，只有明确的结算数据写回 `RunState`，不把整个战斗对象带入下一场战斗。

### 7.2 局内状态

`RunState` 保存一局游戏内的跨战斗数据：

- 当前关卡和路线
- 灵石
- 当前牌组、武器、法宝和符箓
- 已解锁图鉴
- 随机种子
- 当前难度

### 7.3 局外状态

局外存档只保存：

- 道行
- 永久解锁
- 设置
- 图鉴进度
- 历史最高难度

局外不保存每场战斗的临时对象。

## 8. 输入方案

工程当前使用旧 Input Manager。主战斗界面以鼠标点击、拖拽和 UI 导航为主，因此有两种实现路径：

| 方案 | 适用情况 | 结论 |
|---|---|---|
| 旧 Input Manager | 仅键鼠 MVP，尽快验证玩法 | 保持现状，不新增包 |
| Input System | 手柄与键鼠同为 MVP 目标 | 在 UI 实现前引入，避免后期替换输入模块 |

若选择 Input System：

- 使用 UI Action Map。
- 鼠标和手柄共用 `BattleCommand`，不允许两套战斗逻辑。
- 键位提示和手柄提示由 UI 层处理，不进入战斗核心。

## 9. 存档与配置

- 配置数据使用 CSV 作为编辑源，运行时加载为只读 Definition/Database。
- 存档使用可序列化的普通 DTO。
- 存档必须带 `version` 字段，后续通过迁移函数升级。
- 不在配置数据中保存运行时状态。
- MVP 使用 `Resources` 加载 CSV 配置；内容规模增大后再评估 Addressables。

## 10. 代码约束

- 单个方法尽量不超过 60 行。
- 简单分支优先使用三元表达式，但不牺牲可读性。
- 非必要不判空；只在边界输入、配置缺失和外部数据处做防御。
- 公共规则抽到 Helper 或 Calculator，不复制粘贴伤害公式。
- 新增脚本不手写、不手改 `.meta`。
- 不顺手重构无关模块。
- 关键路径失败可以 Warning；不要为每个可空节点刷日志。
- 空方法、未接线能力和假实现必须写 `TODO`，说明未实现范围。

## 11. 编译与验证

每次代码改动后至少执行：

1. Unity 编译检查。
2. EditMode 测试。
3. 进入 `Battle` 场景手动跑一次完整回合。

技术选型评审阶段无代码改动，因此本阶段不产生编译项。
