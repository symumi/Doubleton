# 05｜开发计划与验收

> 版本：v0.1｜依赖：[README.md](README.md)

## 1. 开发策略

按垂直切片推进，不先铺满内容。

优先级：

```text
可运行的单场战斗
  > 规则正确和预览一致
  > 内容数量和视觉包装
```

每个阶段必须形成一个可运行、可验证的闭环。

## 2. 阶段规划

### P0：工程基线

目标：让后续代码有稳定的数据和运行基础。

任务：

- 建立 `docs/program` 文档基线。
- 确认是否引入 Input System。
- 确定命名空间和脚本目录。
- 建立八卦、卦象、武器、敌人和状态的基础枚举。
- 建立配置数据库加载入口。
- 建立 EditMode 测试目录。

验收：

- Unity 无编译错误。
- 配置数据库可以加载。
- 8×8 卦象生成测试通过。

### P1：战斗垂直切片

目标：一场战斗可以完整打完。

任务：

- `BattleState`
- `BattleController`
- `BattleCalculator`
- `BattleResolver`
- `PlayHexagramCommand`
- `EndTurnCommand`
- 手牌、牌堆、弃牌堆
- 灵力
- 内外卦选择和 64 卦查询
- 伤害预览和结算
- 敌人回合和意图
- 胜负结算

验收：

- 鼠标完成一整套出牌流程。
- 预览伤害等于实际伤害。
- 敌人意图与执行一致。
- 战斗可以胜利或失败。
- 逻辑测试全部通过。

### P2：战斗系统补全

目标：达到 MVP 战斗规则覆盖。

任务：

- 武器 3 种
- 法宝 5～10 个
- 符箓 3～5 个
- 状态效果完整接入
- 附魔槽 FIFO
- Boss Modifier 基础框架
- 事件播放和伤害详情
- 快速连续点击保护

验收：

- 至少形成 2 条可区分构筑路线。
- 法宝加算和乘算顺序可验证。
- 附魔槽、状态层数和持续时间无异常。

### P3：局内循环

目标：从单场战斗扩展到一局游戏。

任务：

- `RunState`
- 路线和战斗节点
- 战斗结算写回
- 坊市
- 奇遇
- 牌组增删
- 灵石
- 存档和读档

验收：

- 可以连续进行至少 3 场战斗。
- 战斗结束状态正确写回。
- 坊市购买和删牌可以影响下一场战斗。
- 存档后重新进入可以恢复局内进度。

### P4：MVP 内容与打磨

目标：完成策划文档定义的 MVP 范围。

任务：

- 8 种八卦牌 × 1～3 星
- 64 卦全部可合成
- 16 个精修特殊卦
- 3 种武器
- 约 20 个法宝
- 约 8 个符箓
- 6 小怪、3 精英、2 Boss
- 图鉴
- 局外解锁
- 性能和 UI 适配

验收：

- 单局 30～40 分钟。
- 第 3 境 Boss 前可以形成稳定构筑。
- 无严重卡顿、卡手死局和结算错误。

## 4. 测试计划

### 4.1 逻辑测试

| 测试项 | 断言 |
|---|---|
| 64 卦矩阵 | 8×8 全部可生成 |
| 内外顺序 | `kun_qian` 与 `qian_kun` 不同 |
| 五行克制 | 金 vs 木 = 1.5 |
| 五行被克 | 木 vs 金 = 0.67 |
| 同属性 | 对敌 = 0.85 |
| 伤害管线 | 加算先于乘算 |
| 预览 | 不改变状态 |
| 预览/执行 | 最终伤害一致 |
| 状态 | 层数、持续时间和触发正确 |
| 附魔 | 第 4 个顶替第 1 个 |
| 随机 | 同种子同结果 |
| 胜负 | HP 为 0 后停止继续结算 |

### 4.2 手动测试

- 只选一张牌时不能出卦。
- 灵力不足时不能出卦。
- 选中卡牌后切换选择，预览即时更新。
- 出卦后卡牌进入弃牌堆。
- 结束回合后敌人按意图行动。
- 敌人死亡后不再行动。
- 玩家死亡后不再进入下一回合。
- 战斗中快速点击不会重复扣灵力或重复发牌。

## 5. Definition of Done

一个功能只有同时满足以下条件才算完成：

- 代码编译通过。
- 逻辑测试通过。
- 手动流程通过。
- 不修改无关模块。
- 不手改 `.meta`。
- 未实现能力有明确 `TODO`。
- 文档与实现一致。
- 没有把规则计算塞进 UI。
- 没有新增无必要的第三方依赖。

## 6. 风险与应对

| 风险 | 应对 |
|---|---|
| 64 卦效果写成大量硬编码 | 统一 `EffectOperation`，特殊卦只做字段覆盖 |
| 预览与实际伤害不一致 | 共用 `BattleCalculator`，MVP 禁止随机伤害 |
| UI 先完成但规则不稳定 | 先做纯逻辑测试，再接表现层 |
| 法宝乘区膨胀失控 | 固定加算/乘算顺序，限制槽位和触发次数 |
| 输入系统后补成本 | 手柄属于 MVP 时尽早引入 Input System |
| 配置数据缺少校验 | 编辑器验证和运行时加载使用同一套校验 |
| 局内状态污染下一场战斗 | 战斗结束只写回明确结算 DTO |
| 动画阻塞玩法验证 | 逻辑先结算，表现事件可逐条播放 |

## 7. 下一步

建议先执行 P0 和 P1，具体顺序：

1. 锁定 Input System、同属性系数、品级和附魔计时。
2. 建立基础枚举和配置数据结构。
3. 实现纯 C# 战斗计算器。
4. 用 EditMode 测试验证 64 卦和伤害公式。
5. 接入主战斗 HUD。
6. 完成一场可玩的垂直切片。

在 P1 验收前不扩展坊市、奇遇、局外成长和大量内容。
