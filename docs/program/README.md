## 4. 开发原则

### 4.1 垂直切片优先

先完成一场能玩、能结算、能验证核心乐趣的战斗，再补坊市、奇遇、局外成长和大批量内容。

垂直切片必须包含：

- 8 种八卦牌和完整的 64 卦组合查询
- 手牌、灵力、出牌、弃牌、回合结束
- 内卦先选、外卦后选的顺序规则
- 统一伤害计算和实时预览
- 至少 1 把武器、1 个敌人、2 个基础状态
- 玩家回合、敌人回合、胜负结算
- 一组可自动运行的战斗逻辑测试

### 4.2 预览与结算同源

禁止 UI 单独计算预估伤害。

所有伤害预览、实际结算、详情浮层都必须调用同一个 `BattleCalculator`，保证：

```text
预览伤害 = 实际基础结算结果
```

如果存在随机伤害，MVP 阶段优先改成确定性规则；无法确定时，必须明确显示概率或伤害区间。

### 4.3 数据驱动

静态内容使用 ScriptableObject 配置，运行时状态使用普通 C# 对象。

禁止为 64 卦、法宝或状态各写一套独立类。优先使用：

```text
Definition + EffectOperation + RuntimeState
```

### 4.4 最小架构

MVP 不引入：

- ECS/DOTS
- DI 容器
- 自研事件总线
- Addressables
- FairyGUI / ET
- 复杂行为树
- 多人或服务端

`ink-monster` 的编码规范仅作为通用约束参考，不迁移其 ET/FairyGUI 体系。

## 5. 当前必须锁定的决策

| 决策 | 建议 |
|---|---|
| 输入方案 | 若手柄属于 MVP，立即引入 Input System；否则先保持旧输入 |
| 同属性系数 | 对敌结算统一采用 `×0.85`，与原型图一致 |
| 牌品级 | MVP 使用 1～3 星，4 星留到后续 |
| 附魔计时 | 以玩家回合开始/结束为统一计时边界 |
| 伤害随机 | MVP 不使用随机伤害，保证预览与结算一致 |
| 伤害精度 | 使用整数或万分比定点数，避免浮点显示偏差 |
| 特殊卦覆盖 | 只覆盖指定字段，未覆盖字段继续走内卦 × 外卦模板 |
